# Research Core 事件整合機制設計(獨立於 B2)

狀態:**已整合到正式網站(獨立階段,見 §6)。** 事件機制 + 彈窗/最佳策略頁的真實進度列 + 策略實驗室的球形網絡面板;「重播」只留在獨立原型 `static/prototype/research-core-v2.html`(測試/展示用)。

## 1. 原則(來自你的要求)
1. **「正在工作」的光點與路線必須有真實工作證據。** 每一個光點、脈衝、進度數字、節點狀態,都由**後端真實發出的事件**產生。沒有事件 → 不亮。
2. **不複製 JEV 的 DEMO 自動輪播。** 沒有定時切換情境、沒有 `setInterval` 假進度、沒有編造的「AI 思考」。
3. **不為了視覺效果增加背景運算。** 後端沒有任何執行緒、排程或計時器;事件只是「既有分析流程在開始/完成時順手記一筆」。沒帶 job 代號的請求(卡片、舊流程)完全不記錄,成本為零。
4. 可保留**少量裝飾**(球體緩慢旋轉與變形、淡色環、塵點),但標示為裝飾、低幀率、可關閉,並且**不使用「運算中」的視覺語言**(不產生光點/路線亮起)。
5. 不增加付費 API / Token / 持續性費用;不顯示金鑰、持倉、帳號或機器人狀態。

## 2. 事件從哪裡來(後端)
`research_events.py`(只含資料結構與鎖,沒有執行緒/計時器)+ `app.py` 內的掛鉤。

呼叫方式:前端在分析請求加上 `&job=<隨機代號>`(8–64 個 `[A-Za-z0-9_-]`)。後端在 `/api/analyze`、`/api/best_strategy`、`/api/deep_analysis` 外層建立事件工作;**回應內容不變**(測試比對有/無 job 的回應完全相同)。

| 階段(stage) | 後端真實工作 | 事件內容(皆為實測值) |
|---|---|---|
| `data` 行情資料 | `fetch_data()` 下載/讀取已收盤 K 棒 | 開始:代號、時框、來源(ccxt/yfinance);完成:K 棒數、**實測耗時**;失敗:原因、取得根數 |
| `indicators` 指標計算 | 分析頁的 EMA/策略進出場條件計算 | 完成:K 棒數、耗時 |
| `backtest` 策略回測 | 單一策略 `run_backtest()`;或排名時**每一個策略各一次** | 單一:交易筆數、耗時;排名:`i / n`、策略代號、該策略**實測耗時**、目前入選數 |
| `signal` 訊號判斷 | 由回測交易紀錄推出策略目前持倉/過期狀態 | 完成:是否持有、是否過期 |
| `validation` 樣本外驗證 | `build_validation()`(單一)或排名前 N 名各做一次 OOS | 每名:`i / n`、策略、OOS 筆數、耗時;完成:OOS 筆數與展示分級 |
| `summary` 風險與成本 | `build_backtest_viz()`:權益/回撤/買進持有/成本 | 完成:曲線點數、交易筆數、耗時 |

- 排名/深度分析**不含**指標、訊號、摘要三階段 → 後端明確送出 `skip` 事件(「排名流程不含此階段」),畫面顯示「未涉及」而不是假裝亮起。
- 沒有樣本外(資料太短或快速模式)→ `validation` 為 `skip`,不會有任何驗證光點。
- 失敗(例如資料不足)→ `error` 事件並停止;後續階段不會出現。

事件格式:`{seq, t(自工作開始的毫秒,後端實測), stage, status: start|progress|done|skip|error, …細節}`。
上限:最多 40 個工作、每工作 600 筆事件、閒置 10 分鐘清除。

## 3. 畫面怎麼拿到事件(前端)
- **即時**:使用者按「開始真實分析」才發出分析請求;**只在這個請求進行中**,每 250 ms 輪詢 `GET /api/job_events?job=…&after=<seq>`(只回新事件;這個端點不做任何運算)。請求結束後再取最後一批就停止。待機時完全沒有輪詢、沒有網路。
- **重播(只存在於獨立原型,不在正式網站)**:`traces/traces.js` 是**這台電腦上實際跑出來**的事件紀錄(`tools/record_trace.py` 呼叫真實分析後原樣存檔,未編輯),按原本的時間間隔重播,畫面註明「重播(非即時)」與錄製時間。這是為了在不重跑 20 秒分析的情況下展示/截圖。
- 輪詢而非 SSE/WebSocket:Flask 開發伺服器長連線容易占用執行緒;輪詢只在分析期間存在,簡單且不增加待機成本。
- 輪詢頻率:有新事件 300 ms,沒有新事件逐步放慢到 1 秒;分頁在背景 1.5 秒(事件保留在後端,不會遺失);連續 5 次失敗就放棄;最長 15 分鐘;請求結束後再取最後一批。每次只回傳 `seq > after` 的新事件(一次完整的 166 策略深度分析:約 15 次輪詢、合計約 28 KB)。
- 每個工作一個獨立 job 代號(`rc-` + 72 位元隨機);後端以代號分開保存事件,測試證明兩個同時進行的分析事件互不混入。

## 4. 畫面元素與證據對照(沒有證據就不會出現)
| 畫面效果 | 證據 |
|---|---|
| 節點轉為「執行中」(青色、脈動) | 該階段收到 `start`/`progress`,且尚未 `done` |
| 一顆光點沿路線流向某節點 | **每一個**真實事件(start/progress/done)各一顆;排名時 163 個策略就有 163 顆(同屏上限 90,超出只影響畫面取樣,事件紀錄不遺漏) |
| 路線發亮 | 最近 0.9 秒內該階段收到事件;路線起點是**實際執行過的上一個階段**(排名時是 資料→回測,不經過未涉及的節點) |
| 節點外擴光環 | 真實的 start / done / error |
| 中央面板文字、卡片進度條 | 事件的 `i / n`、策略名稱、耗時、筆數 |
| 節點轉綠 / 紅 / 虛線 | `done` / `error` / `skip` |
| 中央球體亮度、旋轉略快 | 近期真實事件的衰減量(沒事件時為 0) |
| 待機時的球體旋轉、變形、淡環、塵點 | **裝飾**:標示為裝飾、固定低幀率、可取消勾選、不使用光點/路線 |
結果摘要(報酬、PF、OOS 筆數與分級…)來自 API 實際回應,不是動畫腳本。

## 5. 資源控制(依審查意見調整後)
**後端**:事件記錄 = 一次加鎖 + 一次 list append;沒有 job 時是 `NULL_JOB` 空操作;輪詢端點不做任何運算(測試以「呼叫即報錯」的假回測/下載證明)。
**前端**(`rc-engine.js`):
1. **待機是靜態畫面,沒有動畫迴圈。** 迴圈只在「工作進行中 / 事件流動中 / 使用者明確開啟裝飾旋轉」時存在,且要 頁面可見 ∧ 畫布在畫面內 ∧ 非 reduced-motion ∧ 非手機寬度 ∧ 使用者沒關閉動態。
2. **只有真實事件才產生路線光點與脈衝**(每個事件最多一顆光點,同屏上限 60)。工作中但暫時沒有新事件(例如單一策略跑很久)時降到 12 fps。
3. **完成/失敗/取消/中斷後,代表運算中的動畫立即停止**:節點不再脈動、活動度歸零、取消/中斷時光點與光環全部清掉;完成/失敗只讓最後一個事件的光點播完(<1 秒),迴圈隨即關閉並畫最後一張靜態畫面。仍停在「執行中」的階段會被標成「已中止」,不會永遠亮著。
4. **裝飾旋轉預設關閉**(「裝飾旋轉」勾選,使用者開啟過才記在 localStorage);開啟時 10 fps,且不使用光點/路線。`navigator.connection.saveData` 時強制關閉。
5. **分頁隱藏、手機(≤720px)、prefers-reduced-motion、使用者取消「事件流動動畫」、單幀成本過高(自動降頻→靜態)** 時不跑迴圈。手機的畫布只畫球體(狀態由下方節點按鈕格呈現),事件不觸發重畫;桌面靜態模式最多每 400 ms 重畫一次。
6. 進度列不用寬度動畫:`width` 的 CSS transition 每個影格都會觸發排版,實測會讓分析期間的 CPU/GPU 增加一倍以上(見下表 A5 修正前後),已改為事件驅動的離散更新;「處理中」的不定長度條只動 `transform`(由合成器處理)。

**實測**(無頭 Edge 但**啟用這台電腦的真實 GPU:RTX 3080**;CPU = 瀏覽器所有行程合計 ÷ 牆鐘時間,單位為「佔用單一核心的百分比」;GPU = 這些行程的 Windows `GPU Engine` 3D 使用率;每個情境重複 2–3 次取中位數;原始數字在 `validation/stage3_ui/RC_integration/resources_report.json`):

| 情境 | CPU(單核%) | GPU 3D % | 主執行緒忙碌 % |
|---|---|---|---|
| 待機(預設:靜態、裝飾關) | ≈0 | 0 | 0 |
| 待機 + 使用者開啟「裝飾旋轉」(選用) | 11.9 | 0.13 | 2.3 |
| 分析中,事件流動動畫開(真實 SOL-USD 1H 深度分析,約 21 秒,183 個事件) | 15.1(三次:39.5*、15.1、13.5) | 0.27 | 3.7 |
| 分析中,事件流動動畫關(文字/進度列仍即時更新) | 3.8 | 0.10 | 0.8 |
| 分析中,分頁在背景(以引擎的可見性掛鉤模擬;迴圈已停) | 4.6 | 0.08 | 0.8 |
| 分析中,prefers-reduced-motion | 4.0 | 0.11 | 0.8 |
| 分析完成後待機 | 0.8 | 0 | 0 |
| 手機尺寸 待機 / 分析中(簡化) | 0.5 / 5.0 | 0 / 0 | 0 / 0.6 |
| 對照:整合前原型 v2 待機 | 6.5 | 0.14 | 2.5 |
| 對照:同一份真實紀錄重播(約 6.5 秒)舊 → 新 | 22.2 → 19.8 | 0.45 → 0.51 | 9.2 → 8.4 |

\* 第一次含瀏覽器暖機(JIT、首次繪製)。事件流動動畫的額外成本約 11% 單核,只存在於分析進行的那幾十秒;其餘時間為 0。GPU 使用率在這台 RTX 3080 上低於 0.5%。**對交易機器人的影響**:瀏覽器端的負載遠小於一個核心的 1/6,且只在分析期間;分析本身的運算(後端)沒有任何改動,取消/關閉彈窗/關閉分頁還會讓後端提早停止。
限制:這是無頭 Edge 的量測,不是 iPhone 或你平常用的瀏覽器;「分頁在背景」是用引擎的可見性掛鉤模擬(無頭瀏覽器無法真的隱藏分頁);量測當下電腦上同時有交易機器人與其他程式在執行,所以每個情境重複並取中位數。

## 7. 真實進度(取代假進度)
- 進度列只來自事件:後端知道「第 i 個/共 n 個」(例如 166 個策略)才顯示 `策略回測 57 / 166` 與對應寬度;**不知道時顯示「處理中」**(不定長度條,不編百分比)。百分比的意義 = 目前這個階段的真實完成比例,不是整個工作的推算值。
- 事件在工作進行中逐步送達:測試用「卡住的回測」證明——卡住的期間,輪詢端點已經拿得到前面完成的事件;真實 1H 深度分析 21 秒內,183 個事件分 54 次增量到達(不是結束時一次到齊)。
- 每個分析獨立 job 代號(`rc-`+隨機),事件互不混入(測試:兩個同時進行的排名,各自的事件計數正確)。
- 不為進度重跑策略或重下載 K 線:有/無 job 的回測次數與下載次數完全相同(測試以計數器證明),分析請求只多一個 `&job=` 參數(靜態測試比對 URL)。
- 取消:`POST /api/job_cancel?job=…` 設旗標,排名在**下一個策略開始前**與每個樣本外驗證前停止(`JobCancelled` 繼承 `BaseException`,不會被策略內既有的 `except Exception` 吞掉),回傳 `{"error":"已取消","cancelled":true}`(499),沒有半套結果;真實瀏覽器驗證:取消後後端事件序號不再增加、工作狀態為 `cancelled`。關閉分頁時以 `sendBeacon` 通知後端(bfcache 的 pagehide 不取消)。
- 清理:執行中的工作閒置 10 分鐘清除;已結束的工作只保留 2 分鐘(夠前端取走最後一批);每個工作最多 600 筆事件、全部最多 40 個工作;清除只在有人建立/讀取工作時發生,沒有計時器。輪詢最長 15 分鐘、連續失敗 5 次即放棄。
