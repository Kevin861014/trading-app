### 固定與雜湊

- `MANIFEST.json` + `MANIFEST.sha256`:快照的 SHA-256;策略檔(`sim.py`、`integration/extra_strats*.py`)、D2 模擬器(`d2_sim.py`)與 D4 程式的 SHA-256;git HEAD;Python 版本。
- **每次 tick 都先驗證雜湊;任何一個不符就拒絕執行**(不抓資料、不寫帳本)。要改任何條件,只能建立新的實驗版本(新資料夾),不能覆蓋舊的。

## 2 運作方式

```
d4_init.py   建立固定實驗(一次)                      → experiments/<id>/config_snapshot.json, MANIFEST.*
d4_tick.py   單次 tick,跑完就結束(不常駐)           → 抓新收盤棒 → 驗證雜湊 → 重播 A、B → 只附加新紀錄
d4_report.py 唯讀報告(從 ledger/ 與 bars/ 讀)        → 精簡 A/B 觀察報告(--save 另存帶時間戳的新檔)
```

- **行情**:只用幣安 USDT-M 永續合約**公開**端點(`/fapi/v1/klines`、`/fapi/v1/fundingRate`、exchangeInfo)。沒有金鑰、沒有私有或寫入端點。K 棒只收『開盤時間 + 週期 ≤ 現在 − 5 秒』的已收盤棒;儲存時再檢查一次,每根記錄抓取時間。A、B 共用同一份行情檔,所以同一時間看到的行情完全相同。
- **計算**:直接呼叫 D2 已校準的 `d2_sim.run`(只追加『記錄』欄位,不改任何計算;D2/D3 結果逐筆驗證不變)。訊號用每根棒結尾的最近 400 根已收盤棒計算並快取(append-only);視窗有缺棒就不產生訊號。
- **處理範圍**:`T1 = min(最後一根已收盤 1H − 1 小時, 所有幣 1H 從開始起連續不缺的最後一根)`,所以落後現在至少約 2 小時(等資金費率公布)。缺棒時處理停在缺口之前並記錄,**不補造資料**;缺的棒之後補齊會從缺口續算。
- **重啟安全(不重複記帳)**:每次 tick 從固定開始時間『確定性重播』到 T1,再用**事件 id**(`情境|類型|組合|時間`)和帳本比對,只附加新的事件。中途當機(檔案寫到一半)時,殘缺的最後一行會被隔離到 `ledger/corrupt_lines.jsonl`,下次 tick 補寫缺的事件。已有 id 的事件**永遠不覆蓋**;若重算結果與原紀錄不同,只會寫進 `ledger/divergences.jsonl`。
- **單一執行**:`tick.lock`(O_EXCL);超過 30 分鐘的舊鎖視為前次異常中斷,接管並記錄。
- **原始決策保存**:每筆事件記錄決策時間、決策那根的開盤時間、`recorded_utc`、`tick_id`。K 棒不被覆蓋:交易所之後若回傳不同數值,只記錄為 `bar_mismatches`。

### 即時前向 vs 補跑(證據分類)
每筆決策與每個小時權益點,在**第一次記帳**時就寫入下列欄位(之後永不改寫):`bar_close_ts/utc`(訊號 K 棒收盤時間)、`inputs_fetched_utc`(決策用到的行情實際取得時間)、`tick_wall_utc`(tick 執行時間)、`record_lag_s`(記帳距離最後輸入 K 棒收盤的秒數)、`is_backfill`、`evidence`、`backfill_reasons`。
- `LIVE_FORWARD`:記帳延遲 ≤ **8 小時**(快照內固定的 `live_max_lag_ms`:2 小時結構性延遲 + 6 小時 tick 間隔),且之前沒有任何中斷/缺口/修訂/補跑。
- `BACKFILL`(`is_backfill = true`):記帳延遲或行情取得延遲超過 8 小時(例如程式很久沒跑、開始後很晚才第一次 tick)。
- `AFTER_INTERRUPTION`:延遲雖在限度內,但發生在中斷/缺口/修訂/補跑**之後**(模擬路徑已受影響,不是未中斷的即時證據)。
- 旗標另存在 `ledger/data_flags.jsonl`(不可覆寫):`LATE_START`/`INTERRUPTION`(tick 間隔 > 8 小時)、`DATA_GAP`(缺棒)、`BAR_REVISION`(交易所之後回傳不同的 K 棒;已存的原始棒不被覆蓋)。
- 報告第 2 節顯示『已處理到』時間與證據分類;一旦出現汙染,報告會明確標示「不是未中斷的即時前向」,「全部」表標為混合,並另列**只含 LIVE_FORWARD、截至汙染起點**的 A/B 表(第 2b 表)。補跑結果不會被混成未中斷的即時證據。
- **無未來資料**:決策只使用決策時點已收盤的 K 棒,外加『決策當下剛開盤那一根的開盤價』(進場成交參考價與持倉市值,實盤當下也看得到)。測試把決策時點 C 之後的行情全部換成垃圾值(尚未收盤的那根只保留開盤價)重新跑,C 之前的所有決策、成交價、損益逐筆相同。
- 注意:因為處理範圍刻意落後約 2 小時,**每一筆決策的記帳時間一定晚於決策時間**;它之所以仍算「即時前向」,是因為使用的行情與決策當時可得的行情相同,且不是事後才發現能賺錢再補算(證據分類只描述這個延遲與連續性,不代表真實成交)。

### 帳本內容(`ledger/`)
- `events.jsonl`:`ENTRY`、`EXIT`、`FUNDING`、`REJECT`(A、B 各自)。進出場都有:`label: SIMULATED`、`expected_px`(預期成交價:進場為訊號棒收盤、停損為觸發價)、`sim_fill`(模擬成交)、`market_open`/`candle_high`/`candle_low`(實際行情)、`slip_vs_market_open_pct`、`slip_vs_expected_pct`、`fill_within_candle_range`、手續費、持倉量、損益。**模擬成交不會被當成真實成交。**
- `marks_A.jsonl`、`marks_B.jsonl`:每小時權益、錢包、暴露(名目)、持倉數(用來算回撤、最差單日、同時持倉)。
- `ticks.jsonl`:每次 tick 的摘要(新資料筆數、缺口、錯誤、鎖接管、K 棒不一致)。`status.json` 只是衍生狀態(每次覆寫),帳本才是紀錄。

## 5b 資金費率完整性防護(程式版本 d4-v2 起;`paper_trading/d4_funding.py`)
**背景:** 稽核發現模擬器遇到缺漏的資金費率會默默當成 0(沒有錯誤、沒有提示)。真實歷史上確實有這種缺漏:**2026-06-24 04:00 官方 `fundingRate` 對 4 小時制的 JUP、PAXG、PYTH、KAVA、IMX 都沒有這一筆**(間距 4h → 8h → 4h)。這是 D4 啟動前唯一尚需修正的資料完整性問題。

**規則(不假設 8 小時;只用可驗證的結算時程):**
1. 結算間隔只有 1、2、4、8 小時,每一筆都落在該間隔的 UTC 格線上(容許 5 秒內的毫秒偏移)。已用本機 D2/D3 的 50 個序列、209,297 對相鄰結算實測(`validation/d2_portfolio/d4_funding_history_check.py`):**只有上述 2026-06-24 的缺漏被標出,其他 0 筆誤報**(含 14 次真實改制:SOL 2→8、KAVA 1→2→4 與 4→8 等)。
2. 判斷缺漏用的是『相鄰紀錄的間距』:間距不是 1/2/4/8 小時 → 缺漏;不在格線上 → 異常;間距『變長』後下一個間距又『變回較短』(4h → 8h → 4h)→ 中間少一筆;變長但還沒有下一筆可判斷 → 暫停到下一筆出現;變長後持續才是真的改制。
3. 覆蓋範圍:第一筆不得晚於起始時間;最後一筆之後的下一個預期結算(取最近間隔與官方 `/fapi/v1/fundingInfo` 目前間隔較小者)不得已落在處理範圍內。
4. 取得失敗不等於沒有:這次沒有成功取得該符號的費率時,只能處理到『上次成功取得的時間 − 2 小時』。

**發現問題時:** 先向官方從缺口前一筆重新要一次(只附加沒有的紀錄,不改既有);仍有問題就**停止處理**:處理範圍停在缺口之前(不補造、不跳過、不當成 0),tick 記錄、`status.json`、報告與 `DATA_GAP` 旗標都會列出**符號、時間範圍、原因**(例如 `TRX/USDT 2026-11-07 16:00:00 → 2026-11-08 08:00:00:相鄰結算間距 16.000 小時…`)。缺口之後的紀錄會被標為『中斷之後』,不混入未中斷的即時前向證據。永久缺漏(像 2026-06-24 那種交易所自己沒有的紀錄)會一直停在那裡,**需要你決定**(例如另開新實驗版本),不會自動跳過。
**已知限制:** 這個檢查無法分辨『交易所真的沒有結算』與『官方 API 漏列但實際有扣費』,所以兩者都會停止,交給你判斷;此規則建立在『結算間隔為 1/2/4/8 小時且對齊 UTC 格線』上,若交易所日後改變規則,會先以『異常』停止而不是默默繼續。

**與既有實驗的關係:** 這個修正改了被雜湊的程式(`d4_engine.py`、`d4_feed.py`,新增 `d4_funding.py`)。**`d4-v1` 的快照與帳本完全沒有被修改**(快照 SHA-256 開頭 `931a1f7f…` 不變、`bars/`、`ledger/` 仍是空的),但它的雜湊基準對不上新程式,所以 `d4-v1` 會被拒絕執行(這是設計的行為)。要開始 D4 必須建立新版本(例如 `d4-v2`);`docs/d4_snapshot_preview.json` 已更新成新規則的預覽(只是預覽,**沒有建立任何實驗**,版本代號與開始時間由你決定)。

## 6 限制(報告第 4 節也會列出)
- **成交是模擬**:進場 = 訊號棒後下一根 1H 開盤 ×(1+0.03%);真實成交可能因流動性、延遲、拒單、部分成交而不同。模擬成交偶爾略超出當根高低點(開盤±滑價),會照實標記並統計 `fills_outside_candle_range`。
- **不模擬**:交易所拒單、斷線漏輪(假設機器人一直在線,收盤後約 13.8 秒處理)、連敗斷路器、手動操作、帳戶保證金模式差異。
- **模擬器中斷**:程式沒跑的期間不會「漏掉」行情(下次 tick 依已存的已收盤棒補算),但這代表模擬的是『一直在線的機器人』,不是你電腦實際的在線狀況。
- **資料缺漏**:缺棒時處理停在缺口前並記錄;若交易所永久缺那根棒,處理會一直停在那裡,需要你決定(例如另開新實驗版本),不會自動補造。缺口後的訊號需要重新累積 400 根連續棒。
- **資金費率**:處理範圍落後 ≥ 2 小時才算入;使用交易所公布的歷史費率。**缺漏不會被當成 0**:見下一節『資金費率完整性防護』。
- **樣本與解讀**:前向期間短、樣本少;A/B 的差異可能只是雜訊(D3 已顯示 B 歷史上回撤與成本較低,但沒有一致的報酬優勢,也沒有真正獨立的 OOS)。
- 程式碼若有任何修改,既有實驗的雜湊就不符,會被拒絕續跑;需要建立新的實驗版本。
- 雜湊是對工作目錄中的檔案內容計算。觀察期間請不要對 `sim.py`、`integration/`、`validation/d2_portfolio/d2_sim.py`、`paper_trading/` 做 `git checkout`/`reset`/換分支(換行字元被改寫也會讓雜湊不符;不符時 tick 只會拒絕,不會壞資料)。
